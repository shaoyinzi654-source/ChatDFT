新增功能

  • Mayer 键级：由密度矩阵直接得到，零额外 SCF。给出每根键的键级、 每个原子的 Mayer 价、总键级。
  • Hirshfeld 电荷：用与分子同一基组的球平均基态自由原子 密度做权重。这是三种划分里唯一适合写进论文的——加极化函数后它只动千分之几个电子， Mulliken 会动零点几个。
  • Properties 面板新增键级表（带条形图）与第三根电荷条；叙述里引用电荷和与密度积分 作为可信度证据。

第一步：先判定 Mayer 约定，再写代码

Mayer 键级有两个都在流通的定义，闭壳层分子上差恰好 2 倍：

自旋分辨：B_AB = Σ_{μ∈A,ν∈B} [ (PαS)_{μν}(PαS)_{νμ} + (PβS)_{μν}(PβS)_{νμ} ] 总密度： B_AB = Σ_{μ∈A,ν∈B} (PS)_{μν}(PS)_{νμ} P = Pα + Pβ

两者都"看起来合理"，而差别只是每条键除以 2——没有文献对照就发现不了。 用 B3LYP/6-31G* 实测：

分子键总密度约定自旋分辨 文献值
N₂N–N2.829 1.414~2.83 总密度
COC–O2.419 1.210~2.40 总密度
水O–H0.807 0.403~0.80 总密度
甲烷C–H0.964 0.482~0.97 总密度
苯C–C1.456 0.728~1.45 总密度

第二步：Hirshfeld 的自由原子必须球平均

Hirshfeld 权重是 w_A = ρ_A^free / Σ_B ρ_B^free。第一周期原子 全都是开壳层（C 是 ³P，N 是 ⁴S，O 是 ³P），所以未经球平均的自由原子 密度是各向异性的。后果不是"稍微不准"，而是化学等价的原子拿到 不同的电荷：

水的 Hirshfeld 电荷OH(2)H(3) 刚性旋转 37° 后最大漂移
球平均（本实现）−0.31792 +0.15896+0.15896 3.0×10⁻⁵ OK
不平均（朴素写法）−0.29149 +0.15821+0.13328 2.37×10⁻² 790×

两个氢相差 0.025 e——在一张论文表里这足以被解释成"两个氢环境不同"， 而它们其实完全等价。

这条守卫差点变成无效守卫。我的实现按构造就强制径向剖面， 所以"旋转不变性"这条测试对它永远会通过——它测不出球平均有没有做。 要让它有意义，必须把朴素实现写出来当对照，并证明对照会失败。 上面右列就是这个对照。没有它，这条测试只是装饰。

本轮我犯的七个错

这一轮值得单独记下来的是：大部分时间花在修我自己的东西上， 而每一条都是闸门抓到的，不是我读代码读出来的。

1. 转置写错，N₂ 从 2.83 变成 2.04

正确的求和是 Σ M[ra,rb][μ,ν] · M[rb,ra][ν,μ]。我写成了 blk * blk.T——对方形块（N₂ 的两个氮 AO 数相同）它不报错， 只是给出一个错误的数：2.041。既不是 2.829 也不是 1.414，是一个 看起来还挺像键级的数。对水则直接崩溃（O 的 14 个 AO 对 H 的 2 个， 形状不匹配）。

ValueError: operands could not be broadcast together with shapes (14,2) (2,14)

要不是拿 N₂/CO 的文献值做了对照，2.041 会被当成"合理的部分双键"收下。

2. eval_rho 在这个构建里根本不能用

PySCF 的 numint.eval_ao 在这里返回 (N, nao) （文档也这么写），而 eval_rho 内部按 (nao, N) 处理：

AssertionError (numint.py:711, lib.dot(dm.T, ao.T))

项目里 fields.py 早就不用 numint，而是走 mol.eval_gto。 新模块改为复用同一个 density_and_gradient——顺带保证"场的图"和 "电荷表"不会对密度是什么产生分歧。

3. 断言了一个我自己写错的诊断量

铵离子那条报 weight_sum_fraction = 0.144295，看起来像"权重不是单位划分"。 但电荷和 0.99996 是对的。原因：Σ_A w_A = 1 只在有密度的格点上 成立，而 86% 的网格权重落在分子外（那里 ρ_pro < 10⁻¹²）。我断言的量从一开始就选错了。 改成断言逐格点偏差（<10⁻⁹）后才成立。

4. 字段名写错：narration vs explanation

"叙述必须提到键级"这条检查报失败，但叙述其实是好的——作业对象里的字段叫 explanation。一个检查因为读错字段而失败，和一个功能因为没实现而失败， 在输出里长得一模一样。修的是测试，不是功能。

5. 每步 SCF 都跑一次成键分析

第一版把分析放进 _harvest，于是每一次 SCF 都会做一遍—— 包括偶极导数循环（6N 个位移点）、键扫描的几十个点、几何优化的每一步。改成 DFTEngine(bonding=True) 显式开启，只有填充 Properties 面板的两条路径 （单点、几何优化）付这个代价。

6. 自由原子的 SCF 想写检查点文件

PermissionError: [Errno 13] unable to open file: '...\Temp\tmp0wwv5n48'

一次性原子不需要检查点；mol.chkfile = mf.chkfile = None 之后正常。

7. 新加的 DOM id 和已有 id 撞了（唯一一个真实产品缺陷）

键级表我起名 id="bondTable"——但 Geometry 面板 300 行之下已经 有这个名字，装的是感知出来的键列表。不会报任何错： $('#bondTable') 返回文档里第一个匹配，于是新表会渲染到 另一个面板里，并覆盖掉由另一条代码路径填充的列表。

抓到它的是项目自带的 check_selectors——它的职责就是把 app.js 里每一个 选择器对着 index.html 解析一遍，其中包含重复 id 检查：

DUPLICATE ids: ['bondTable'] === FAIL === - duplicate ids in index.html: ['bondTable'] check_selectors FAIL (exit 1) 0 checks <-- 套件记 9/10

而且闸门运行器把"非零退出且没有任何判定行"判为失败，所以一个还没打印就死掉的闸门 不会被当成通过。改名 mayerTable 后复跑：DUPLICATE ids: none。

教训：在单页应用里加 DOM id 之前先 grep 一遍；名字要按功能限定 （mayerTable）而不是通用（bondTable），因为通用名会撞。
