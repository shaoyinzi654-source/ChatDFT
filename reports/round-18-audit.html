ChatDFT 审计 · 第 18 轮

数出来的内存常数、位移的标尺、以及变异台自己的异常 · 2026-09-16

本轮从一个门禁失败开始。它已经连续多轮通过，这次报的是：

nmrmissing: the thiophene job ended failed -- NMR at 6-31g* needs about 2.5 GB for this molecule (82 basis functions) but only 2.0 GB of physical memory is free right now.

机器内存被其它应用占到只剩 1.5–2.2 GB，所以这个拒绝看上去是环境问题。但 拒绝里那个 2.5 GB 是从哪来的？它来自一个常数乘 nao⁴，而那个常数—— 代码注释里逐项列出了它的来源——从来没有人拿它和一次真实运行比过。 本轮把它量了，量出来它低了 23%。随后顺藤摸瓜又找出两个缺陷。

缺陷 1：内存守卫的常数低了 23% 严重

它是怎么来的

nmr.py 里的注释写得很整齐，看起来无懈可击：

# at the worst point four arrays of that size are live at once -- # real ERIs 8 bytes per nao^4 # the three GIAO ERI derivatives 24 # one pair-swapped direction 8 # the complex ERIs of a perturbed SCF 16 # -- i.e. 56 bytes per nao^4. _BYTES_PER_NAO4 = 56

问题是这是一张数组清单，不是一次测量。清单里没被算进去的东西——构造 每个方向的那次变换的临时数组——正好是那缺掉的四分之一。

量出来是多少

probe_mem1 用 psutil 以 20 ms 间隔采样 shielding_tensor 的峰值 RSS，基线取在 build_operators 之后，所以算子本身不 计入，测到的就是屏蔽机制的代价：

分子nao实测峰值按 56 的估计
水186.4 MB5.9 MB
氨208.6 MB9.0 MB
甲醛3272.2 MB58.8 MB
乙醇54584.3 MB476.2 MB

nao⁴ 从 1.05×10⁵ 到 8.5×10⁶，跨 55 倍。四点落在一条过原点的直线上： 斜率 68.8 字节/nao⁴，截距 +0.2 MB，R² = 0.99997。甲醛那点最能说明问题—— 按 68.8 预测 72.1 MB，实测 72.2 MB。

低估的后果，早就记在同一个文件里

这是本轮最值得记下的一处：available_mb() 的文档串里一直写着 一次事故，却没人把它和那个常数联系起来。

The first TMS reference was measured at 5165 MB against a 6000 MB budget -- which passed -- on a machine that happened to have 1 GB free at the time, so it swapped and took 4829 seconds instead of the 285 the same calculation took on an idle machine.

5165 MB 正是按 56 算出来的（56 × 98⁴ ÷ 10⁶ = 5165）。按 68.8 算， 同一个作业是 6346 MB > 6000 MB 预算——它本该被直接拒绝，而那次著名的 一小时磁盘交换根本不该发生。守卫低估四分之一，就会少拒四分之一，而下面那个 1.25× 的可用内存余量并不能真正兜住 1.23× 的误差。

修法：常数改 69，注释写入四个分子、斜率、R²、截距作为依据。

契约里那条断言本身就是缺陷的一部分

旧写法是这样的：

need = _n.memory_estimate_mb(98) if not (4000 < need < 6500): fail.append(f"nmrmem: nao = 98 (TMS at 6-31G*) must be estimated at about 5.2 GB")

它复述的是模块手里那个常数，所以只能抓「有人改动了它」，永远抓不到「这个数 是错的」——56 在这个区间里舒舒服服待了好几轮。这正是「检查被缺陷本身致盲」： 检查的参照物和被测对象来自同一个错误来源。

改为在被测出来的单位里断言，带宽足以容纳另一台机器的分配器行为，又 窄到装不下 56：

per_nao4 = need * 1e6 / 98 ** 4 if not (60.0 <= per_nao4 <= 80.0): fail.append(f"nmrmem: the estimate implies {per_nao4:.1f} bytes per nao^4; " f"the peak was measured at 68.8 (probe_mem1, nao 18..54, " f"R^2 0.99997) ...")

改完这个常数，我自己造出了一个回归

预算检查是 need > MEMORY_BUDGET_MB，而预算是 6000 MB。 按数出来的 56，TMS 是 5165 MB，在预算下留 16% 余量；按量出来的 69，同一个参考 是 6364 MB——超过预算 6%。这个比较根本不看空闲内存，所以在一台 128 GB 的机器上一样会拒。

probe_mem4 实测：

budget 6000 MB, constant 69 bytes/nao^4 ammonia nao= 20 need 11.0 MB fits chloroform_f nao= 82 need 3119.6 MB fits methane nao= 22 need 16.2 MB fits phosphine nao= 24 need 22.9 MB fits tms nao= 98 need 6364.3 MB REFUSED water nao= 18 need 7.2 MB fits

而它只在冷缓存上才会发生：reference_shieldings 先读缓存， 读不到才走到 check_memory。所有门禁都是在 TMS 缓存已热的情况下跑的， 所以一个全新安装会丢掉全部 ¹H、¹³C、²⁹Si 位移，而没有任何一条门禁会说话。

修法：预算提到 7500 MB（对最大参考保留和原来 6000 MB 相同的约 18% 余量， 同时仍然拒绝当初设立预算要拦的规模——nao = 200 是 110 GB），并新增一条断言： 每一个参考化合物都必须放得进预算。这条断言只问预算、不问空闲内存，所以 机器再忙也不会把它弄红。

这一条值得单独记下来，因为它的形状和本轮缺陷 1 完全一样，只是换了一层： 一个检查的参照物和被测对象来自同一个错误来源，就抓不到那个错误。旧的 4000 < estimate < 6500 复述常数；而「预算能装下参考物」这件事 从来没有被任何断言表达过，因为写它的人只知道 5165 那个数。

缺陷 2：两个核的位移不在 IUPAC 主标尺上，而且只字未提 严重

每个位移都带着参考化合物的名字，这一条一直是满足的。但名字不是标尺。 按 Harris 等（Pure Appl. Chem. 73, 1795 (2001)）列出的 IUPAC 主 参考：

核IUPAC 主参考本程序用是否一致
¹H / ¹³C / ²⁹SiTMSTMS一致
¹⁷OH₂OH₂O一致
¹⁹FCFCl₃CFCl₃一致
¹⁵NCH₃NO₂（硝基甲烷）NH₃差 380.2 ppm
³¹P85% H₃PO₄ 水溶液PH₃偏移未计算

两个不一致都是有原因的，而且原因值得写下来：

  • ¹⁵N：主参考硝基甲烷是 66 个基函数，按修好的常数约 1.3 GB。液氨是 公认的次级标准，所以数不算错——但它离论文常用的标尺 380.2 ppm。
  • ³¹P：主参考是 85% H₃PO₄ 水溶液，那是混合物，气相程序根本算 不了；纯 H₃PO₄ 是 85 个基函数、约 3.5 GB。

为什么这件事必须说：380 ppm 比大多数官能团的整个 ¹⁵N 范围还大。用户拿本程序 的 ¹⁵N 位移和论文比，会把这整段标尺差读成计算错误。

修法：标注，而不是换参考

新增 IUPAC_PRIMARY 表与 scale_note(el)。关键设计是 它和 REFERENCE_FOR 比对，而不是存一个布尔标志：将来真把 硝基甲烷加进参考表，标注会自己消失，而不是变成一句陈旧的谎言。

每个核的条目带 reference_scale_note，在主标尺上是 None 而字段存在——调用方才能区分「在主标尺上」和「没人想过标尺」；同一句话 也进警告列表，并且在 references[el].scale_note 里再带一份，前端把它 渲染成参考化合物名字旁边的一枚警示标签。最后这一步是刻意的：本项目记过 「无人消费的字段」这种缺陷——字段算对了、断言也过了，就是没人读，等于没做。 实测氨的载荷：

N delta 0.000 ppm note: N is quoted against NH3, not the IUPAC primary reference CH3NO2 (nitromethane, neat liquid). sub... elements ['H', 'N']; field present on ['H', 'N']
关于 ³¹P 的那个数字。我查到 380.2 ppm 是有出处的（氨标尺→硝基甲烷标尺 减去 380.2）。³¹P 我只找到可外推的数据：UCSB 表给 PMe₃ −62、PMe₂H −99、 PMeH₂ −163.5，外推 PH₃ ≈ −240。按本项目的规矩，外推值不写进产品。所以 ³¹P 的标注改为写明「偏移是 PH₃ 自己在 H₃PO₄ 标尺上的位移，本程序不计算它； 它不小，不得假定为 0」。缺一个数就说缺一个数，不拿估的顶替。

缺陷 3：变异台自己的异常捕获，被自己的 reload 顺序废掉 工具

噻吩被内存守卫拒绝时抛 DFTError，而它从 make_payload_thiophene 里穿了出去，整个变异台崩溃退出。这是 最坏的一种结果：一个崩溃让其余 20 多个变异全都跑不到，报告看起来像「什么都没 抓到」，真相是「什么都没跑」。

第一次修法我写了 from backend.engine.dft import DFTError—— 仍然崩。原因很有意思：reload_engine() 先重载 nmr 再重载 dft，于是 dft 的 DFTError 变成了 新类对象，而 nmr 手里还攥着旧类对象。两个不同的类， except 新类抓不到旧类。改成 except N.DFTError——抛出 异常的那个模块自己持有的类——就与 reload 顺序无关了。

同时把 thiophene 那一组如实记为 SKIPPED：run_checks 拿不到 载荷就不会走到 nmr_unreferenced_sections，那条断言不可能失败。把 「从未运行」报成「没抓到」，比报成「跳过」更糟。

缺陷 4：14 个核「没有参考」只是一张清单，没有理由 记录

README 一直写着 14 个 NMR 活性核没有参考化合物（Al B Br Cl D Hg I Li Na Pb Pt S Se Sn），但不说为什么。一张没有理由的清单，正是缺口变成传说的方式：没人 分得清哪些是决定、哪些是遗漏。实测下来它两者都有，而且理由各不相同。

先量清楚哪些是基组问题

用 gto.basis.load 直接问基组（probe_ref1）。这里我 自己先踩了一个坑：第一版探针去建裸原子，结果把 Al、B、Br、Cl、Li、Na、D 全报成 「NO BASIS」——真相是 Electron number 13 and spin 0 are not consistent， 闭壳层检查在基组被查之前就抛了。14 条理由里有 7 条差点写错。

原因元素依据
6-31G* 里根本没有Hg I Pb Pt Sn BasisNotFoundError
标准是溶液不是分子 Li Na Al Cl Br S LiCl/D₂O、NaCl/D₂O、Al(NO₃)₃/D₂O、NaCl/D₂O、NaBr/D₂O、 饱和 (NH₄)₂SO₄/D₂O（³³S 跨度 964 ppm，−290 至 674）
标准是分子但装不下B BF₃·OEt₂：19 原子、nao=146、30.6 GB，预算的 4 倍（probe_ref2）
既非不可能、也还没做Se D 都在基组里，⁷⁷Se 与 ²H 都可以有分子参考——记为缺口，不记为理由

六条「溶液」的理由值得展开：气相孤立离子的屏蔽不在这把标尺上，而卤素阴离子 还需要 6-31G* 没有的弥散函数。算出来的会是一个「穿着别人标尺名字」的数——正是 ¹⁵N/³¹P 那两条标注要防的那种错。

修法：把理由变成代码里的一等数据

新增 NO_REFERENCE_WHY，理由进入用户看到的告警（不再只是名字）， 并加一条断言把两个集合绑死：理由的键集必须恰好等于「NMR 活性但无 参考」的元素集。于是加参考就必须删理由、删理由就必须加参考，两边无法各自漂移。

nmrref: the unreferenced nuclei are ['Al', 'B', ...] but the reasons cover [...]; missing reasons [...], stale reasons [...]

缺陷 5：³¹P 能算，却没有任何一个分子能按名字取到 功能缺口

上一轮结尾记下了这个缺口：分子库 62 条里一条含磷的都没有。³¹P 有参考化合物、 有标尺标注、在同位素表和谱图通道里都有位置——却没有任何一个可以按名字取到的 分子。这个功能只对已经知道 SMILES 的人存在，而没有任何一条门禁能发现它， 因为所有门禁都在测零件，没有一条在测接缝。

为什么不能直接加 PH₃

PH₃ 就是 ³¹P 的参考化合物，而「库里有该参考物就用库几何」这条规则会把参考从 实验 r_e 换成 RDKit 松弛出来的几何，整条 ³¹P 标尺随之移动。这不是舍入 误差：本项目实测过，两个 PH₃ 几何之间 ³¹P 屏蔽差 2.819 ppm。所以加了 一个邻居，而不是参考物本身。

加了一对，而不是一个

分子nao内存估计δ(³¹P) vs PH₃耗时
甲基膦 CH₃PH₂420.21 GB +66.409 ppm11.4 s
二甲基膦 (CH₃)₂PH600.87 GB +107.340 ppm24.5 s

选一对是有意的：连续甲基取代是 ³¹P 的经典趋势，而一个把趋势当卖点的程序， 应该能在它刚学会的核上展示一条。两个都足够便宜，可以在门禁里反复跑。

方向对，绝对值不可核对。每次甲基化使 δ 更正——计算与文献趋势一致， 间距也在合理量级。但绝对位置取决于 PH₃ 到 85% H₃PO₄ 的偏移，而那正是本程序 不计算的那个数。这恰恰是标尺标注存在的理由：数字给了，但说清楚它站在 哪把尺子上。

把它变成一条规则

缺口之所以能存在，是因为没有人把覆盖规则说出来。现在它是一条断言， 放在库被加载的地方：每一个有参考化合物的核，都必须至少被一个库条目携带。 它只比较两个内存里的集合，不花任何计算。变异 L21（拿掉那两个磷条目，还原成本轮 之前的状态）精确命中。

缺陷 6：一个变异体从未运行过，有两个各自独立的原因 严重

补 ³¹P 覆盖时顺手做了一件事：给分子库加一个含磷分子。加完之后去核对变异台， 发现 L20 每次都以「mutation not applicable」收场——不是失败，是根本没跑。 而且它有两个各自独立的原因，任何一个都足以让它永远不触发。

原因一：查找键不匹配，默认值把错误吞掉了

变异台要改的文件按标签查表：

MUTATION_FILE = {"L20": ELE} # 键是短码 ... path = MUTATION_FILE.get(label, MOL) # 传进来的是完整标签

而循环传的 label 是完整标签 "L20 bond-perception-misses-dihydrogen"。于是查找落空， dict.get 静默回退到默认文件 molecule.py——那个文件里 当然没有目标串，于是报告「不适用」。一个静默吸收键不匹配的默认值，把「从未 运行的测试」变成了「什么都没抓到的测试」，而默认值本身是有用的（另外 5 个 变异确实住在 molecule.py），所以不能简单删掉它。

原因二：变异台自己的 reload 不包含被改的文件

把键改对之后，L20 仍然不触发。真因在 reload：

for mod in ("backend.engine.molecule", "backend.contract"): # 没有 elements importlib.reload(sys.modules[mod])

L20 改写的是 elements.py 里的 H–H 键长阈值，而契约那侧是 from backend.engine.elements import bond_cutoff——它返回的是 sys.modules 里那个没被重载过的旧函数。所以无论变异怎么写都 不可能生效。这和 NMR 变异台那个「重载顺序产生两个异常类」是同一类缺陷：变异台 自己的机制废掉了自己的测试。

而且它还因为错误的原因「触发」过

修好前两项之后，L20 报出了 4 条失败——但前 3 条全是 propane 的遗留字段，属于 变异台给每个代码变异注入的 legacy-schema 噪声（那是给两个读取器变异用的）， L20 自己那条根本不在里面。这正是本项目记过的「多个变异同时施加，成功看起来 一样」。现已改为只给需要它的两个变异注入，L20 现在只报一条，就是它自己 那条：

MUTATION L20 bond-perception-misses-dihydrogen -> 1 failure(s) raised: library/hydrogen: its coordinates fall into 2 piece(s) but the SMILES '[H][H]' names 1. A structure that is not connected the way its own name says is not that molecule

并在启动时加了一道检查：任何键不是真实标签、或目标串不在它所指文件里，直接 拒绝运行（probe_p6 验证了它两半都会拦）。

这是本轮第三次遇到同一形状的缺陷——报告说「什么都没抓到」，真相是「什么都没 跑」。前两次是 NMR 变异台的异常类（重载顺序）和它崩溃时把其余变异一起带走。 一个测试套件最危险的状态不是红色，是绿色而从未运行。

  • _BYTES_PER_NAO4 的实测只有四个点、最大 nao = 54；nao = 82 和 98 处仍是线性外推。斜率看起来干净，但没人验证过。
  • 14 个无参考核（Al B Br Cl D Hg I Li Na Pb Pt S Se Sn）目前只是告警。要正式 记录为何不提供：6-31G* 只覆盖到 Ar，而其中 Cl/Li/Na/Al 的 IUPAC 标准都是 水合离子——气相孤立离子算出来的屏蔽，对水合标尺没有意义。
